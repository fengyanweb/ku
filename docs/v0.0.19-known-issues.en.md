# Ku 0.0.19 known issues

[中文](v0.0.19-known-issues.md) · [Release notes](v0.0.19.en.md)

0.0.19 is an experimental prerelease. This page retains confirmed limitations and unexplained failures without turning historical checks, short tests or isolated examples into general production guarantees.

## Default Runner toolchain mismatch

The original public 0.0.19 `ku build hello.ku` can select its 1.89 runtime by modification time while invoking another system rustc, producing E0514. Source MSRV does not lock compiler selection. An independent candidate adds exact bundle manifests, compiler-identity selection, `ku doctor` and unified help; **these are not in the original public assets**. Website documentation cannot retrofit an old installation, and C-backend success does not establish a default Runner fix. See [CLI / Runner candidate notes](cli-runtime-bundle.en.md).

## Latency and stability

- **Historical HTTP 504s remain unexplained.** They occurred historically and were not uniquely reconstructed by the latest short recheck; evidence for the earliest three is insufficient. They are not marked as fixed. Formal 30-minute sustained acceptance has not passed, and open-ended historical investigation is not being continued.
- **Cancellation-phase p99 passed a short test; rare tail spikes remain.** The last valid sequence was normal load for 30 seconds → overload for 3 seconds → recovery for 15 seconds → cancellation for 30 seconds → recovery for 10 seconds. All 60,000 short requests in the cancellation phase were correct: exact p99 1.557 ms, maximum 98.809 ms, with 169 above 20 ms. Post-overload recovery had p99 1.606 ms, maximum 54.246 ms and 74 above 20 ms; post-cancellation recovery had p99 1.420 ms and maximum 3.751 ms.
- Those cancellation tails formed one cluster and included client generation/handoff delays as well as time after the first write. Complete same-RID server-side attribution is missing, so they cannot all be charged to Ku execution. Tails have also occurred without cancellation; neither cancellation code nor the host is established as the sole cause. The original 378 slow requests were clustered observations in one window, not 378 independent failures.
- The first two rechecks encountered other-project load and swapping, with generator p99 above 5 ms; they are invalid for service-SLO scoring. The last valid window did not observe the identified unrelated builds/tests, which does not prove an entirely idle machine. The short test did not remeasure actual cancellation-stop or physical-reclamation time. Deliberate-overload rejections, timeouts and other HTTP errors remain separately recorded.
- The historical phase4 p99 failure of 25.761695 ms remains on record. The five candidate windows and formal 1,800-second acceptance have not been run. The current decision is to stop pursuing the rare spikes for now, without longer deadlines, less frequent checks or speculative runtime patches.

The last valid cancellation recheck used runtime source `418de2a` and normal-service binary SHA256 `5d337c2ef159e5d21a44ca2eb3ccab50f2fc0e9128a583b50abe88c67eb36ffc`. This is a historical measurement identity, not the identity of the final Release artifacts.

## Functional and resource boundaries

| Area | Current boundary |
| --- | --- |
| Task and backends | Native C supports only its listed async subset. Full M:N scheduling, fully suspendable interpreter execution, general network waiting and complete blocking-library coverage remain incomplete. A successful static check does not establish support on every backend; see the [concurrency contract](concurrency.md). |
| Two paused areas | General value copying/freeing and further AST analysis remain paused. Specific repaired call/cleanup paths do not establish coverage for every depth or function graph. |
| JSON | The previous default and shared interfaces remain, including the large-float round-trip fix. Values such as `1.0` and `-0.0` need not retain their float type tag or negative-zero sign; integer overflow remains an error. yyjson replacement and performance exploration are closed. |
| PG and other databases | Existing real-database results are not a complete platform matrix. Pool rejection, timeout and unknown outcome must be distinguished. Database operations are not automatically retried, and worker termination does not prove rollback. |
| Service recovery | Multiple instances on one host, process replacement and example rollback do not establish node-level availability, a real production canary or data rollback. A real application, target SLO and production rollback destination require their own acceptance. |
| Resource accounting | Task/HTTP capacity ledgers are not process RSS. Complete per-Task heap accounting and precise per-Task attribution of shared pools, caches and external-library memory are unavailable. No sustained growth in a bounded observation does not prove the whole project leak-free. |

Linux hard limits in `ku supervise` require a writable, delegated cgroup v2 hierarchy with the required `memory`, `pids`, `cgroup.kill` and related interfaces. They constrain kernel-accounted memory, not an invariant that instantaneous RSS can never exceed a number. Windows uses Job committed-memory limits, a different metric from RSS or Linux accounting; allocation failure need not become a normal Result. Native macOS explicitly rejects this isolation mode; ordinary execution and ordinary `ku service` remain available.

`ku supervise` does not itself impose an OS hard limit on its coordinator. Worker limits do not automatically cover external databases, build processes or the host. External whole-unit limits require separate configuration and verification; there is no absolute whole-system memory-cap claim. The existing 36 over-limit recovery checks retain their original identities and were not needlessly repeated in this round. They do not substitute for sustained HTTP acceptance. See [process execution](process-execution.md).

## Delivery status

Official package targets are macOS ARM64, Linux x64 and Windows x64 only. The Linux ARM64 source-build performance environment is not one of those three packages. Historical isolated RC rehearsals and final-version CI/package verification are accounted for separately; a skipped release job is not a successful release. The seven-language fixed-load short comparison is complete; the full capacity and sustained-load matrix was not run. Website work in this round is code and packaging only, without deployment.
