# Ku 0.0.13

0.0.13 的重点是把用户已经会直接碰到的工具链路径闭合：标准库 root import、诊断帮助、项目 build、release 二进制和 VS Code 插件版本必须一致。

## 标准库导入和导出规则

- 标准库 root import 允许小写模块名：`import { task, time } from "std"`。
- 用户自己写的顶层 `fn` / `struct` / `enum` 仍按 Go 风格：首字母大写才导出，小写只在当前文件私有。
- import/export 错误会同时给出位置、问题描述、note 和 help。例如误写 `Task` 会提示标准库模块名应小写，并给出 `import { task, time } from "std"` 方向。

## 二进制构建命令

新增稳定的 build 命令入口：

```powershell
ku build [file.ku]
ku build .
ku build -o <path> [file.ku]
ku build --release [file.ku]
ku build --profile <debug|release|small|fast> [file.ku]
ku build --target <target> [file.ku]
ku build --emit-c [file.ku]
ku build --emit-ir [file.ku]
ku build --emit-llvm [file.ku]
ku build --backend c [file.ku]
```

`ku run build` 保留兼容，但会输出：

```txt
warning[W0101]: `ku run build` is deprecated
help: use `ku build` instead
```

默认 build 仍是解释器打包型可执行文件：入口源码会嵌入一个 Rust wrapper，输出到 `.ku/build/<profile>/<name>`，Windows 自动加 `.exe`。这条路径能稳定产出可运行二进制，但不是最终 native ABI；带 import 的程序仍需要原源码依赖路径可访问。

## ku.mod

`ku.mod` 新增 build 字段：

```txt
name = "demo"
version = "0.1.0"
root = "src"
main = "main.ku"
out = ".ku/build"
cache = ".ku/cache"
```

无显式文件时，`ku build` 使用 `root + main` 作为入口；`main` 默认 `main.ku`，`out` 默认 `.ku/build`。

## std.time

`time.from_millis` 会验证毫秒值是否在当前时间后端支持范围内。超出范围会报错，不再静默回退到当前时间。

## async task 最终用户模型

- `async fn` 调用会立即启动一个轻量 task，并返回一次性 `Task<T!>` 句柄。
- 普通开发者只保存 async fn 返回的 task，再用 `await task` / `await task?` 等待；`await task?` 等价于 `(await task)?`。
- `await` 会消费 task，普通 task 只能 await 一次；重复 await 会报 `E0804` 并提示保存已 await 出来的值。
- `Task<T>` 是 owned、move-only，不能隐式复制，也不能 `clone()`。
- Ku 不提供 `task.spawn`、`Task.new`、`runtime.schedule`、`thread.spawn` 或普通 task 生命周期方法。
- `std.task.stats/stress` 仍保留为 runtime 诊断和压力测试工具，不是任务创建或调度 API。
- HTTP server 内部可以使用 task 处理并发，但 handler 用户不需要手动创建或管理 task。

## VS Code 和发布产物

- VS Code 插件版本同步到 `0.0.13`。
- release 目录需要同步新的 `ku.exe` 和 `libku.rlib`，否则 PATH 上的旧 `ku` 会继续报旧的 std import 错误。
- `release/使用说明.md` 已更新 HTTP 示例，不再出现旧的 `std:http` / `http.try_get` 写法。
