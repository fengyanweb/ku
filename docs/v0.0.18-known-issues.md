## 资源与平台保证

- `ku supervise` 限制的是明确启动的整个 worker 程序及相应资源域，不是每个 HTTP 请求，也不是每个 Task 的精确堆用量。
- Linux 需要具备 `memory`/`pids` 委托和 `cgroup.kill` 等必需接口的 cgroup v2；按内核计费量执行 worker/合计限制，可能发生内核合同允许的瞬时越限，不是 RSS 每时每刻精确封顶。
- Windows 使用 Job Object 的提交内存限制，不能与 Linux 计费量或 RSS 视为同一指标；初始进程创建阶段的提交另有明确边界。
- macOS 原生拒绝该隔离模式，拒绝发生在启动用户程序前；普通 `ku run` 和 native 执行仍可用。Linux VM 必须显式准备并运行 Linux 版 Ku，没有自动转发。
- 协调器自身没有 OS 硬限制；控制容量/队列/输出预留不等于它的精确 RSS 账本。单 Task 堆、共享池、缓存和外部库内部分配没有逐 Task 完整拆分。
- worker 的内核限制不保证第三方库的所有内存不足都返回普通 Result。超限可终止 worker；协调器须如实报告、回收并继续后续独立程序，不自动重放数据库操作。

具体条件、指标和现有 36 次超限回收验证见 [受控进程执行](process-execution.md)。
本次收尾不无故重复这些验证，也不把它们当成 HTTP 长期验收。
