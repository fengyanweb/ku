# Ku 0.0.20：平台要求和已知问题

- 原生 C、解释器及其他输出路径的覆盖不同；以对应功能文档和实际编译结果为准。数据库 client 使用原生路径及其客户端库。
- native C 尚不支持 `http.json(http.status.created, value)` 这一状态常量写法；使用等价整数 `201`，或使用解释器／默认 Runner。此限制在 0.0.19 与 0.0.20 均可复现。
- `ku supervise` 的 Linux 进程内存限制需要 cgroup v2 的可写委派、memory controller 和对应权限。缺少这些条件时不能获得该模式的硬限制。
- Windows 通过 Job Object 限制受控 worker 的提交内存；该指标不等于 RSS。macOS 原生不支持这套隔离执行模式。
- worker 的 OS 上限覆盖其进程中的第三方库分配。协调器自身没有同等 OS 硬限制，单 Task 堆也未精确计量；Task／HTTP 分配账本不能解释成整个系统内存绝对封顶。
- 某些负载历史上出现过长尾和 HTTP 超时，根因未全部确认，原正式长时间验收尚未通过；本版不宣称这些问题已全部修复或长期稳定性已完成。
- 数据库取消、期限检查与发送之间仍有时序边界；临近该边界的操作可能到达数据库。终止 worker 或断开连接不等于业务必然回滚。结果不确定时必须按不确定处理，运行时不自动重试业务 SQL。
- 完整通用网络调度、完整 M:N、数据库完整平台矩阵及部分性能目标仍未完成。不要将单项功能通过或历史局部结果外推为所有场景完成。

CLI／SDK、编译器和目标库应保持同批身份。源码开发使用固定 Rust 1.99.1；既有旧版本包继续使用其自身元数据中记录的编译器，不会因为本版发布而改变。
