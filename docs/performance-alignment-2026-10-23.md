# Ku 性能与资源对齐：实施及验收记录

本记录对应《Ku_Go_Rust性能对齐与资源领先_完整实施任务书_2026-10-23.md》。本轮仍在实施，不能把以下研发预检写成正式性能达标。网站、已发布 r1 资产及两个暂停模块均不在修改范围。

## 身份与判断规则

- 旧生产基线：`cac47df6b1db6a3bbd4eebf470306221ca4ef13c`，生产路径与既有 `8abb9bc` 相同。
- 集成候选：`257c8827fbbe65b2a4b55dbea89e7e06de9e952f`，含后续API、容量、计数、槽复用与七栈驱动；七栈49个微型内容窗口392/392正确，不代表性能验收。
- 第一候选：`1bdf88326461a11938f17609a618dbc27e4753d1`，含 Task 计算路径、HTTP 活动索引、RST 处理和旧 JSON 编码器改进。
- 压测驱动 V5 与后续 API／容量变更分别记录身份，不拼接成第一候选的结果。
- 每个核心场景分别对 Go、Rust 判定。吞吐比 95% 区间下界需 ≥1；相同正确吞吐的 CPU 成本比区间上界需 ≤0.90，稳态及观测峰值内存比需 ≤0.80；尾延迟同时满足原 SLO 与非劣要求。未取得合格样本或未达到目标的行保持未验收。

## 已定位的开销及实际修改

### CPU：计算与执行框架分开

旧 Linux 证据中，单核独立计算每次 CPU 为 Ku 2.20ms、Go 2.38ms、Rust 2.04ms；同算法经 HTTP 的原成本明显更大。两组运行条件不同，不能相减后宣称精确框架成本。

本轮按同一生成程序插入有界计数（只用于诊断，不用于正式测速）：每次 512000 迭代，原版与候选都执行 2048003 个逻辑状态、32001 次 frame drive，原 64 状态让出边界不变。完整 frame 检查 544004→32004，动态 selector 2080003→32002，空作用域退出调用 512000→0。跨状态存活槽 21→5，frame 464→336B，Task 实例 960→832B。减少的是重复检查、分派及常驻中间值；原整数校验、取消、错误位置和让出要求仍保留。

Mac 研发预检 7 轮配对，完整进程 CPU 成本均值比 0.880，95% bootstrap 区间 [0.848,0.926]，校验和全部正确。此为同机候选研发结果，不能充当 Linux 单核或对 Go／Rust 的正式验收。原用户 async 格式化 helper 的 Task 身份没有被偷偷删除；公开 str 原语新增直接 Task IR 路径，原 helper 与新的正常 API 用法分表比较。

### CPU：仅在单次 drive 内缓存 Copy 标量

第二候选把已验证的 int/bool/null 持久槽暂存在单次 drive 的 C 局部变量，实际返回前写回。拥有型值、初始化位、Task/lease 仍留在原 frame；有 finally 或借用槽的函数不启用。64 个原逻辑状态的让出频率不变，取消、算术错误和跨让出存活回归通过。

同一新 ABI11 生成 C，仅替换两个 drive 函数，frame 定义先逐字核对相等。设 KU_EVENT_LOOPS=1，但不宣称 CPU pinning。首个8批次研发点 CPU 比均值0.925、区间[0.867,1.017]，证据不足；原始点保留。预先延长为每进程128批次，仅补该不确定点，7轮全部改善，配对均值0.90394、区间[0.89409,0.91464]；进程CPU中位0.579898→0.525739秒，观测maxRSS中位同为1785856B。全部计算结果和正常退出已核对。此为局部研发证据，Linux端到端收益仍未验收。

### JSON：普通字符串逐字符输出

原编码器每个正常字符都调用缓冲追加逻辑。候选对连续的无需转义片段合并写入，中文／emoji 仍逐标量验证 UTF-8，转义、NUL、长度上限、浮点及错误规则沿用旧实现。没有更换 JSON 库，也没有改变子树访问的所有权语义。

仅替换同一生成 C 的字符串 writer，clang C11/O2、每轮 10000 次、7 轮配对、三种现有语料，完整结果均独立解析核对。全进程 CPU 比值如下（均为 Mac 研发预检）：

| 数据 | 仅编码 CPU 比 | decode／读取／重建／encode 完整链 CPU 比 | 结论 |
| --- | ---: | ---: | --- |
| 对象 | 0.619 [0.589,0.636] | 0.824 [0.816,0.835] | 字符串输出成本下降 |
| 数字数组 | 1.006 [0.991,1.032] | 0.997 [0.992,1.000] | 未见明确变化 |
| 转义文本 | 0.558 [0.549,0.573] | 0.699 [0.687,0.712] | 字符串输出成本下降 |

以上不是 HTTP 全链收益，也没有证明对 Go、Rust 领先。必要的 19 条既有 JSON 回归均通过，覆盖 Unicode/NUL、整数／浮点及 1e20、输入／输出大小、深度、错误、OOM 和部分构造释放。

### HTTP：活动槽与确定的连接重置

原事件循环反复扫描配置的全部槽。候选维护 owner 本地活动表、空闲链及 slot/generation 就绪映射，处理实际活动对象。CLOSED_JOB／CLOSED_ASYNC 保持在活动表，等真正退休后才释放槽。

新增真实 socket 回归先复现：客户端 RST 后，等待中的 timer Task 仍驻留。原因是 JOB／ASYNC 阶段不观察 HTTP socket。候选只在就绪事件中 peek：确定的读错误请求取消；FIN 是合法写端半关闭，不能据此取消；下一请求字节也不消费。FIN／pipeline 观察后暂停该读兴趣，防止反复唤醒。后台执行责任和预算保留到物理退出。

错误诊断使用固定原因计数、最多 8 个内部样本，只有令牌保护的管理接口可读取。request id 仅保留前 48 字节，以 hex 表示并标记截断；不记录正文、指针或凭证。样本优先保留 HTTP 500，普通 503 不会淹没它；外部 HTTP 状态不因此改写。未知 500 单独计数，不能归入普通容量拒绝。第一候选的 Linux 有界复现已取得新样本：

- 双核 120rps、5秒，600／600 正确，无 500。全生命周期 CPU 3.745377秒，即 6.242295ms／正确请求；驱动后仅 0.000157秒 CPU，最终 Task／队列／HTTP 缓冲为零。它只有 600 个样本，不作为核心公开 p99／正式容量点。
- 双核 960rps、5秒，4800 计划，客户端 223 正确、3389 个 503、1188 次超时，客户端未收到 500。服务内部却生成了 139 个 500，全部分类为 `task_limit`，`unknown_500=0`。8 个样本有 request id、父 Task ticket/generation、owner 和执行阶段。父 Task 曾开始执行（非 InlineFailed 根准入），子 Task 的失败 Result 经原 `?` 链传播成响应失败；源码链为 `c_task_adapter.rs::start_value_impl → c_task_host.rs::ku_task_value_take/ku_task_value_error → c_task_http.rs::ku_http_task_poll → c_http_runtime.c::ku_http_response_from_result`。
- `LIMIT=9` 当前同时涵盖槽和字节预算。已确认是 Task 准入／预算上限传播，尚不能仅凭该通码断言具体哪一种上限；下一候选补同锁拒绝分支计数后核实。原 503 的通用 fallback 错标为 projection_budget，也已发现，不能据该数字断言 3389 次全部来自 HTTP 缓冲。分类将按实际分支修正。
- 高压代次完整 CPU 37.072111秒，驱动结束后仍使用 21.804045秒 CPU。5秒夹具静默未通过，原服务期限内最终自然归零，无强制终止。合法 FIN 不证明响应已无法交付，因此该尾部 CPU 不能全部命名为“无用工作”。本点是原因复现，不是容量、性能或 ≤5秒恢复达标。

两次均是新候选、原 helper 用法及 V5 驱动；主机回归构建可能重叠，明确不用于正式性能排名。原始窗口与所有终态保留。

37 项 HTTP 回归及 503 后仍保留 500 样本的定向回归均通过。Task IR 73 项直接相关回归通过。并非完整三平台 CI 已通过。

### 网络功能存在但没有等待时的空扫描

源码和计数反例确认：只要服务编入net功能，原每个HTTP turn都调用net interests，即使当前只跑CPU／timer，也在pool锁内扫描整个实际capacity。16384容量、两owner空集合仍访问32768个job。候选在原锁内维护32个owner的NET_WAIT计数，空集合O(1)返回；非空仍用原有限遍历和generation规则。四个NET_WAIT入出转换与解锁step后换代／换owner通过定向回归；CPU占比及Linux单变量收益仍待实际采样。

此前只读定位中怀疑的Task指标全槽扫描，经调用链复核发现正常仅管理接口读取、另一次位于启动失败清理，不在普通每turn；没有为这处误判追加索引重构。

### PostgreSQL 数字读取与会话合同

PgResult.value_int直接检查owned字段span，严格int64 token，不复制字符串、不创建JSON树，保持原value方法和DISCARD ALL。10条相关回归通过，另1条实库opt-in明确未运行；27格式边界、11坏span／NULL等矩阵及close client后独立结果读取已验证。实际PG全链收益尚待比较，不能由少了分配次数直接推断CPU或内存目标达成。

normal表保留各驱动原方式，单独reset-equivalent表才对Go/Rust增加同lease清理、2s原操作期限和250ms获取上限。两表不能混用，不能把对照的正常归池写成已有DISCARD隔离合同。257c882基线PG由同步HTTP后台线程泵进libpq；后续本地候选已将原共享PgClient捕获、query/reset和typed结果接入native Task owner WAIT，保留显式sync变体。该新路径的有限正确性验证见后文，正式性能尚未验收。

### 容量、固定存储与真实配置

HTTP公开上限升至16384 active／32768 connections，Task及network上限16384。CLI普通根默认仍1024，默认Task预算仍16MiB。HTTP按配置分配容量，blocking/poll/network scratch使用有界堆存储并纳入原KU_TASK_MAX_BYTES固定账本；不把大数组塞入线程栈。8320 active／16640 connections、2 owners、16384 Tasks且含net路径的Mac实际固定backing为35473944B，另有活Task、HTTP缓冲、系统栈和外部库成本。正式规格使用原64MiB Task预算，整个进程仍受独立1GiB域约束，两个预算不能混为一谈。

根Task工厂尚未开始时若预算不足，旧入口曾发布InlineFailed而误报HTTP准入成功；已有不足一字节的受控反例，现清理该未启动值并按原规则拒绝。已经开始执行后的子Task错误保持原语义。槽和字节拒绝计数独立记录；不能把1bdf的通用LIMIT样本事后全写成槽不足。

基准将BENCH_MAX_*通过普通config.json字段传给Ku的http.server，普通配置仍为1024／4096／128；等待矩阵要求管理接口实际limits与请求配置吻合。源码已允许更大容量不等于8192实测已通过。

## 测量有效性

V5 驱动使用有界对数直方图，全量计数和终态 CSV 核对；原一百万离散桶上限不再丢弃迟延样本。小于 100 样本不报 p99，小于 1000 不报 p999；核心公开 p99 至少 1000 个对应类型样本。小样本逐轮只报告 observed max，不能称逐轮 p99。正式轮次固定 seed、7 轮交错配对。

独立控制服务 16／128／1024rps、各 5 秒，idle expiry 500ms／0 两种，共六个有效窗口，11680／11680 正确，终态 CSV 全量对账，无 HTTP 500。16rps 每窗 80 样本，p99 为 null，max 约 11.16／11.48ms；128rps p99 4.64／4.14ms，1024rps 1.59／1.61ms。驱动占其三核配额约 0.9%—5.0%，观察到的 service／driver 节流为 0。一个准备操作重叠窗口原样保留并排除，只补了受影响点。该结果没有解释旧代次中的非单调异常，也不能证明任意更高速率的驱动能力。

生命周期账本分为到达窗口、驱动存活期、真实责任完全结束后的完整成本。额外 5 秒夹具门槛单列，继续按原服务期限观察，不提高服务 timeout；强制终止及其尾部 CPU 不得抹掉，也不当作正常退还。无用工作只能对已知无法交付且契约允许停止的区间归因，不能简单把全部尾部 CPU 都叫浪费。
