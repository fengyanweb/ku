# HTTP 延迟诊断与稳定性验收

本阶段针对历史 HTTP 504 与真实服务链路，不代表完整 v0.0.18 已完成。
JSON 继续使用旧默认实现；通用值复制/释放与 AST 后续分析保持暂停。

## 已核实的链路

历史普通负载为客户端直连 loopback 上的解释器 HTTP。没有代理、数据库或
`ku supervise`。一个 I/O reactor 管理 socket，一个解释器 caller 串行执行
handler；完整请求解析后的排队和处理共用 100 ms 期限。它没有经过通用
Task executor。读取超期为 408，队列/准入拒绝为 503，handler 等待或执行
超期为 504；写超期关闭连接。

native HTTP 使用独立固定 handler workers，数据库连接池属于服务进程。
显式使用 `ku supervise --native` 时，协调器管理整个服务 worker，不代理
HTTP、不共享数据库连接、不自动重新启动相同入口，也不重放失败请求。
native 处理期限从实际 handler 调用起算，不能与解释器队列期限混为一谈。

最早三个 504 的逐请求证据已经删除，现有摘要不能唯一定位它们。后续保留
的失败记录证明过排队超期和 handler 墙钟远大于线程 CPU，但不足以单独
认定代理、数据库、宿主调度或缺页为根因。本轮新增复现与旧记录分别报告。

## 正式运行前冻结的要求

主验收保持直接解释器 HTTP 架构。动态 JSON 请求核对请求 ID、整数计算、
中文/emoji/引号/反斜杠/换行/NUL 及 UTF-8 字节数。HTTP/1.1 复用连接；
普通并发最多 8，目标合计 5000 请求/秒，客户端期限 3 秒。固定速率不追补
暂停期间的欠账，另外报告实际达到的速率；未达到目标不能报负载通过。
这是一项有明确余量的稳定性验收，不是最大吞吐或 Go 性能对照。

服务配置保持 connections/active/pending=256/8/32、handler=100 ms、
idle/header/body/write=2000 ms，不通过增加期限掩盖失败。普通阶段要求：

- 每个成功响应核对正文；内容错误、非预期 5xx、传输错误均为零。
- p95 <= 20 ms、p99 <= 50 ms；记录端到端延迟和直方图误差范围。
- 实际完成速率达到目标的 95%；首末相同窗口有效吞吐降幅不超过 5%。

计划共 1800 秒，阶段结束只停止产生新请求并等在途请求完成，不通过取消
旧 context 制造边界 EOF；实际耗时可包含有界排空：

| 阶段 | 时长 | 行为与判定 |
| --- | --- | --- |
| warmup | 30 s | 普通请求，单独统计 |
| ordinary_first | 300 s | 普通负载，计入正式门槛 |
| idle_pressure | 60 s | 最多 128 个空闲/不完整连接，预期有 408/503/关闭；末段排空，恢复 <=5 s |
| ordinary_after_idle | 300 s | 普通负载，计入正式门槛 |
| overload | 30 s | 48 并发调用 250 ms 慢 handler，独立统计预期拒绝/超期，不算成功吞吐 |
| recovery | 5 s | 结束故障注入后 <=5 s 内健康请求返回真实 200/正确正文 |
| ordinary_last | 1060 s | 同一普通负载，计入正式门槛 |
| final_idle | 15 s | 关闭客户端连接，核对 HTTP owner 和预算回到空闲基线 |

取消附加验证使用主动断开/不读响应的真实 socket，核对有界期限后的回收及
后续健康请求；不将主动取消算作普通成功。客户端、资源采样和服务独立记录
UTC/单调时钟。分段日志仅保留有界数值，不保存请求正文或连接凭据。

## 资源与附加服务链路

每 5 秒观察 HTTP pending、handler queue、各连接状态、保留 buffer 字节及
峰值/拒绝/超期来源，并采集进程 RSS、FD、线程。要求计数保持配置上界；
结束排空后 HTTP pending/handler queue/buffer 归零；首末普通窗口 RSS
中位数增长 <=8 MiB，FD/线程无持续增长。RSS 观察不是 OS 硬上限，也不把
`task.stats=0` 当作 HTTP owner 已归零的证据。

诊断使用已有的 `KU_HTTP_TRACE_SLOW_MS=50` 开关，默认关闭。仅接受可选
`x-ku-trace-id` 的十进制 u64 数值；正文、路径、SQL、连接串不进入日志。
生产者向容量 256 的固定事件队列 `try_send`，单个进程级 writer 使用独立
stderr 句柄输出，HTTP 线程不取日志锁、不等消费者，也不在停止时等刷新。
慢日志/transport/快照分别最多 128/256/512 条；超过额度或队列满会计入
`trace_dropped`。诊断可能被截断，不能把未记录的异常解释成没有异常。

transport 的 status 来自最终 wire response，包含预算不足导致的 503 替换。
`publish_attempt_to_observe_us` 从发布尝试前到 I/O 观察到回复；
`response_phase_us` 包括响应编码、等待可写及写出，均不是纯 syscall CPU
耗时。无法取得的阶段为 unavailable。queued/queued_bytes 包含提交前的
输入 owner 预留，拒绝瞬间的峰值可比 channel 容量多一个；字节数不包括
HashMap buckets、allocator 元数据或完整 Task 堆。并发快照不是原子事务。

附加 native HTTP+PostgreSQL 链路使用临时本地只读数据库，核对正常查询、
受控慢查询及后续恢复。Linux 显式 supervise 的服务退出验证只承诺：协调器
存活、旧 worker/预算被回收、预先排队的后续独立服务能启动并接受新请求。
恢复期限 5 秒；连接/事务结果不确定时如实记录，不承诺自动回滚、服务自动
重启或失败请求自动重试。不会无故重跑原有 36 次内存超限组。

正式运行前记录源码/二进制/配置哈希、环境、验收门槛和开始时间。失败保持
失败；新增改动后只重跑与改动相关的验证。一次性脚本、样例副本、构建产物
运行后删除，保留精简结果、哈希和必要失败证据；必要永久回归保留。

### 已确认的原因与尚未确认的部分

独立缺陷已实证修复：旧版stderr管道填满65536B后，慢请求虽先回复200，随后同步日志阻塞解释器caller，健康请求504；排空管道恢复。修复后管道仍满时，健康请求200/1.05ms。必要永久回归覆盖真实管道、日志队列/输出限额、数字ID、预算owner、真实TCP晚回复回收及最终wire状态。这个缺陷不能解释最早trace关闭时的三个504。

未改底层的180秒GOMAXPROCS8复现出现26个504/9个503；其中独立10ms采样器缺失232.296583ms期间，解释器/I/O线程CPU仅推进364/332us。handler270344us墙钟/432us CPU，随后7个排队请求约288ms超期。正式负载早期16个普通504全部匹配数字请求ID：1个handler_expired、3个queue_expired、12个reactor_handler_expired。代表请求handler317946us墙钟/243us CPU，I/O发布观察和响应阶段也等待约100ms。证据定位到执行进度停顿跨过原100ms期限，不能唯一指定OS调度、缺页、allocator或某把锁，也不是本链路的代理或数据库超时。没有证据要求恢复暂停模块的分析。

末轮92个504缺逐请求trace：过载耗尽128/256条生命周期日志上限，最终trace_dropped153238；快照仍持续到结束。另一次60秒、296293个成功响应的10ms调用栈采样没有复现异常，不能由正常栈反推失败栈。另一次180秒不限速/8并发、5ms采样完成6058916个核对200、零错误；这轮同样未复现，不能确认故障等待原因。最早三条旧失败的逐请求材料已不存在，不能唯一还原。当前这些缺口使本阶段仍未收口。

过载保留的64条错误全部为客户端建立连接前的EADDRNOTAVAIL（can't assign requested address），而非HTTP503或服务端写失败；其余9837条没有分类明细。503/504关闭连接造成高周转，本机可用临时端口范围49152..65535；没有当时TIME_WAIT清单，不能把全部错误唯一归为该机制。原正式失败保留。预先另定500RPS/48并发/30秒的补充过载收到13961个503+936个504、零传输/内容错误，2.85ms恢复；它不替代正式结果。
