# Ku 0.0.18

0.0.18 交付本轮已经实现并验证的功能和修复，仍是实验版本，不可用于生产。0.0.x 不承诺源码、生成 C 或内部 Task ABI 向后兼容，旧 native 产物应重新构建。本版不新增或变更项目许可证，编辑器扩展保持 `UNLICENSED`。

按 2026-10-20 的发布决定冻结范围：历史 HTTP 504 保留为已知问题，不再单独阻塞本版。完整 M:N、通用网络调度及数据库完整平台实库矩阵进入后续版本；通用值复制/释放与 AST 后续分析保持暂停。下面的“部分交付”不代表原任务整体完成。

## 本版交付

- 解释器已选定调用、Result、字符串与等待路径的堆帧修复，以及表达式/模式构造界限；保留已有调用、深度和资源上限。更广通用值/AST 路径未据此宣称全部完成。
- native Task 的有限 typed frame/driver、worker 本地队列及工作窃取、timer 和既有 blocking pool 集成；文件/目录操作及局部 TCP 等待走已实现的有界路径。具体支持与拒绝矩阵见 [并发合同](concurrency.md)，不是完整语言和全部库调用都可挂起。
- 修复 blocking producer 与关闭交接中的生命周期缺口，保留 resident 责任直到实际 capture/结果清理完成。复用已通过的永久回归，不宣称所有并发组合都已证明。
- HTTP/1.1 连接复用、请求顺序、pending 准入和有界 transport buffer；修复满 stderr 导致诊断输出阻塞 handler 的独立问题。该修复没有被当成所有历史 504 的根因。
- JSON 保留旧默认实现；`json.encode` / `json.decode` 与既有 JSON 入口共用实现。大浮点输出若没有小数点/指数且超出 int64 文本范围，追加 `.0`，使 `1e20` 等编码后能再次解码；整数溢出继续拒绝，小浮点类型标签和负零符号不保证往返保留。yyjson 替换和性能探索已结束。
- 显式 `ku supervise`：以完整程序为 worker 单元，限制 worker 数、总预留、路径队列及输出；通过支持平台的内核机制约束 worker 资源域，失败回收后处理后续独立程序。数据库操作不自动重试，worker 终止后的副作用可能未知。
- MySQL/MariaDB 无结果语句及连接清理等既有修复；本机或指定客体的实库记录按原环境保留，不外推为全平台矩阵通过。

## 已知问题

**历史出现过 HTTP 504；本轮 60 秒及 180 秒短测未复现，根因未确认，正式 30 分钟验收尚未通过。** 两轮共 1,194,352 次成功响应不能替代长期验收，也不表示历史问题已修复。最早三个 504 证据不足，无法唯一还原。本轮停止针对历史七次 504 的追加诊断及盲目压测。

native C 对源码中的部分大浮点字面量（已记录 `100000000000000000000.0`）可能发射成过大 C 整数 token 而编译失败；该路径不宣称支持。可通过较小的 typed float 变量运算取得大值。这与已修 JSON 大浮点往返是不同路径。其余已修记录、保留限制及证据边界见 [已知问题清单](v0.0.18-known-issues.md)。仅核对已有记录，没有把新猜测扩成发布阻塞。

## 支持平台与内存限制

本版按目标分别提供安装包，没有三系统通用二进制：

| 目标 | 发布验证环境 | supervise |
| --- | --- | --- |
| `x86_64-unknown-linux-gnu` | Ubuntu 24.04 x86_64 | 需要专用、可写、已委托的 cgroup v2 根；`memory`、`pids`、`cgroup.kill` 等条件必须满足，否则拒绝启动 worker |
| `x86_64-pc-windows-msvc` | Windows Server 2025 x86_64 | 嵌套 Job Object 的单 worker/合计**提交内存**限制；受宿主 Job 策略约束，分配失败不等于必然终止或返回普通 Result |
| `aarch64-apple-darwin` | macOS 15 Apple Silicon | macOS 原生不支持该隔离模式，在启动用户程序前拒绝；普通解释器/native 功能仍可用 |

未列出的 CPU/系统组合或更旧 OS 不据此宣称经过发布验收。Linux cgroup 计费量不是 RSS，内核合同允许瞬时越限；Windows 提交内存与 Linux 计费量也不是同一指标。Linux VM 必须自行准备并显式运行 Linux 版 Ku，没有 macOS 自动转发。

协调器自身没有 OS 硬限制；控制预留、队列和输出容量账本不等于其精确 RSS。单 Task 堆未精确计量，共享连接池、缓存及第三方库内存不能逐 Task 精确拆分。普通 `ku run`、构建器、外部数据库、宿主和其他进程不自动受 worker 限额约束，不能宣称整个系统内存绝对封顶。完整条件、失败语义与已有 36 次超限回收结果见 [受控进程执行](process-execution.md)；本次不无故重跑。

## 下载与安装

从 [v0.0.18 Release](https://github.com/fengyanweb/ku/releases/tag/v0.0.18) 下载匹配目标的 `ku-v0.0.18-<Rust triple>.tar.gz`、并列 `.manifest.json` 和 `SHA256SUMS`。只以该页面实际上传的文件为准，`native_ci-*` 不是 CLI 安装包。

1. 先按 `SHA256SUMS` 核对下载文件：Linux 使用 `sha256sum`，macOS 使用 `shasum -a 256`，Windows 使用 `Get-FileHash -Algorithm SHA256`。
2. 将归档解压到新的独立版本目录，按包内 `README-INSTALL.md` 放置整套文件。保持 `ku[.exe]`、`libku.rlib`、`deps/` 与 `native-tls/v1/<target>/` 的相邻布局；不要只复制 CLI 后声称默认 build 的依赖完整。
3. 把该目录加入 PATH，运行 `ku --version`，应输出 `ku 0.0.18`。需要编辑器支持时，在 VS Code 选择 Install from VSIX，安装包内 `ku-language-0.0.18.vsix`。
4. `ku check` / `ku run` 不要求本地 Rust 编译工具链。默认 `ku build` 需要匹配的 Rust 1.89.0 与 linker；C/native 构建需要相应 C 编译器。数据库 native 程序另需匹配 SDK/动态库；安装包不包含数据库服务或 `ku-registry` 服务端。

首次小程序可使用包内安装说明的 hello；JSON 例子见 [examples/json.ku](../examples/json.ku)。源码构建与发布脚本合同见 [history.md](history.md)。最终归档包含逐文件校验与第三方 notices，不改变项目自身许可。

## 发布验证依据

本版要求最终提交的必要三平台 CI，通过真实 host bundle 构建、完整资产校验，再由 `v0.0.18` tag 触发发布任务。发布任务实际生成并公开 Release 后才能宣布完成，历史 job 的 skipped 不算通过。

导出器使用最终归档解压出的 Ku 做版本查询、hello 检查/运行及 JSON 代表程序运行，核对输出和正常退出；manifest 中的安装检查凭据绑定版本、目标、可执行文件与示例校验，发布前再次核对。Release 正文和资产中的 `RELEASE.json` 记录实际提交及 CI 链接。此安装验证不是 HTTP 长期负载，也不改变已知问题状态。
