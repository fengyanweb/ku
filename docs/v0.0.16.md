# Ku 0.0.16

0.0.16 的重点是**补齐 native 标准库**、**接入数据库驱动(PostgreSQL / Redis / MySQL,含连接池)**,并通过路径级所有权分析与对抗式审计加固内存/资源安全。目标始终是:开发快速、占用资源小、稳定、安全。

> **验证状态说明(重要)**:本版本的数据库驱动为 native-only 的新功能,各驱动的真实验证程度不同,请以下表为准,不要把「已实现」等同于「已在生产验证」。
>
> | 驱动 | 验证程度 |
> |---|---|
> | **std.pg** | 统一 client 已通过 fake nonblocking/池/OOM 门槛，并在 Windows loopback PostgreSQL 17.10 完成一次新 API 实库往返；Linux/macOS 和 CI 中的真实服务仍待验 |
> | **std.redis** | bounded client 已通过 Windows fake RESP、并发等待者、延迟销毁和错误恢复门槛；本轮实现尚未重新跑真实 Redis，Linux/macOS 仍待验 |
> | **std.mysql** | `MYSQL_STMT` client 的 fake ABI、OOM、并发 close、清理/reset 失败淘汰、执行结果分类与 header/runtime 错配共 8 项专项已通过；本机 Oracle MySQL 8.0.29 已完成链接/启动，真实查询与 Linux/macOS 仍待完成 |

## 数据库驱动(std.pg / std.redis / std.mysql)

三个驱动只公开一种普通业务入口：`module.client(config)?`。client 是 move-only owned 句柄，内部自动管理有界连接池；查询/命令只借用连接，结果在归还连接前复制到 Ku owned 内存。`close()` 消费 client、立即拒绝新借用，不等待仍在执行的查询或懒建，并由最后一个已经登记的借用者完成延迟销毁；最终底层 socket/library close 仍是同步系统调用。0.0.x 不保留 raw connection、手动 pool、模块级 query 或宽松读取的兼容别名。数据库 C helper 是生成文件内的 `static` 实现细节，不是供第三方绕过 Ku 所有权并发 close/use 的稳定 ABI。

三个驱动的构造前配置校验统一返回 `invalid_config`。通过校验后的 client 构造、池借用和懒建物理连接统一使用下面的错误码；domain 仍是 `pg` / `redis` / `mysql`。命令、查询、结果读取和认证错误不塞进这张表，继续保留驱动自己的精确 code。

| code | 阶段 | 可否直接重试 |
|---|---|---|
| `client_closed` | client 已关闭或空句柄 | 不能；应重新创建 client |
| `pool_busy` | `max_waiters` 已满 | 可在请求总预算内做上游背压，不能无界循环 |
| `acquire_timeout` | 借连接总预算先耗尽，或与独立建连预算同时耗尽 | 仅可按业务幂等性决定；此时尚未发送命令 |
| `connect_timeout` | 独立建连预算严格早于借连接总预算耗尽 | 可做有界退避；此时尚未发送命令 |
| `connect_error` | DNS、socket、握手或驱动建连失败 | 可做有界退避；诊断不包含凭据/服务端反射文本 |
| `sync_error` | client 构造或等待阶段的同步原语失败 | 不建议重试，属于运行环境/内部状态异常 |
| `out_of_memory` | client/连接/池分配失败 | 不应立即重试，应先降载 |

懒建连接失败后，每个 client 同时只允许一个新建连接探测。退避窗口从 25ms 指数增长并封顶 1000ms，实际 equal-jitter 延迟落在 `ceil(window/2)..window`（首次 13～25ms）；已有健康空闲连接不受退避影响。新请求必须先进入等待集合，不能以未排队身份直接夺取空闲槽；集合内由平台 condition variable 无序选择，不保证 FIFO 或无饥饿。每个请求始终保留原 absolute deadline，驱动不会在一次 API 调用内自动重拨或重放命令。负责等待退避到期的线程离开时会把定时唤醒责任交给另一名等待者，避免剩余请求睡到自己的总超时。

PG/MySQL 对明确识别出的 transaction/session-control SQL 在访问连接前返回 `session_state_unsupported`；执行后检测到未结束事务、COPY 或关闭 autocommit 也会丢弃成功 payload、返回该错误并淘汰连接。这里的 SQL 识别只是一条有界的有限语法防线：存储过程、扩展函数或表达式可能产生文本预检无法完整证明的会话、全局或外部副作用。reset/淘汰保护的是下一位池借用者，不保证任意 SQL 本身“无副作用”，也不会把已经执行的语句撤销。普通 client 因而禁止业务依赖跨调用 session 状态；transaction/exclusive API 尚未开放。共享 client 不接受不受信任方提供的任意 SQL；生产账号必须最小权限，PG 不使用 superuser，MySQL/MariaDB 不授予 `SYSTEM_VARIABLES_ADMIN`、`RELOAD`、`FILE` 等非业务权限。

### PostgreSQL(std.pg,绑定 libpq)

```ku
import pg from "std.pg"
fn main(): null! {
    client = pg.client({
        conninfo: "host=... dbname=... user=... password=... sslmode=verify-full sslrootcert=C:/certs/root.crt",
        max_connections: 8,
        max_waiters: 64,
        connect_timeout_ms: 5000,
        acquire_timeout_ms: 5000,
        query_timeout_ms: 30000
    })?
    // 查询永远参数化；无参数时也传 []。
    res = client.query("SELECT id, name FROM users WHERE id = $1", ["42"])?
    println(res.rows())
    println(res.value(0, 1)?)
    client.close()
    return ok(null)
}
```

- 唯一公开入口是 `pg.client(config) : PgClient!`；唯一查询入口是 `client.query(sql, [str]) : PgResult!`。无参数查询也传 `[]`，所以不存在“直接 SQL”与“参数 SQL”两套安全等级不同的写法。结果只通过 `rows()`、`cols()`、`value(row,col)!`、`is_null(row,col)!` 读取；NULL、越界和复制 OOM 都是可 catch 的结构化错误。
- `max_connections` 为 1～256，`max_waiters` 为 0～4096；三个毫秒 timeout 均为 1～300000。conninfo 最多 64 KiB，SQL 最多 16 MiB。构造时预连一条连接验证 conninfo/UTF-8，其余连接懒创建。等待者上限提供有界接纳和背压；连接损坏、查询超时、COPY/BAD_RESPONSE 会淘汰对应槽位；成功查询若留下非 IDLE 状态则丢弃结果并返回 `pg/session_state_unsupported` 后淘汰。懒建时若借用预算先到返回 `pg/acquire_timeout`，只有独立建连预算先到才返回 `pg/connect_timeout`。
- 查询继续使用 `PQsendQueryParams`、nonblocking flush/consume/busy/getResult 和 `PQsetSingleRowMode`。最多 65535 个参数、64 MiB 参数文本；结果最多 100 万行、4096 列、100 万单元和 64 MiB 文本。SQL 已发送但未取得确定终态的 timeout/断连/OOM 返回 `pg/execution_unknown`；已收到成功终态但结果因格式、UTF-8 或上限无法交付时返回 `pg/execution_completed_without_result`。两者都明确禁止自动重试。服务端明确失败仍是固定的 `pg/query_error`，不反射可能包含 secret/control character 的服务端文本。
- 建连、借用和查询使用 monotonic absolute deadline，并受 HTTP handler 剩余预算约束。portable C 无法硬抢占同步 DNS 或 libpq/SSL 内部调用；调用返回后仍会检查截止时间并丢弃过期连接。数据库侧仍必须设置 `statement_timeout` / `lock_timeout`。
- conninfo 可能包含密码：构造失败和 client 销毁都会清零内部副本；建连错误使用固定消息，不复制可能回显 conninfo 的 `PQerrorMessage`。远程生产连接应使用 `sslmode=verify-full` 和可信 `sslrootcert`。
- 明确的 transaction/session-control 首语句在借连接前返回 `pg/session_state_unsupported`；响应结束后仍非 IDLE 也返回该错误并淘汰，不做无界隐藏 `ROLLBACK`。正常归还前在原 query deadline 内用同一 nonblocking pump 执行 `DISCARD ALL`；reset 失败或预算耗尽直接淘汰。该清理保护下一位借用者不继承已知 session 状态，但 SQL 文本预检无法证明存储过程、扩展函数和表达式没有副作用；调用方不能把“未被预检拒绝”理解为允许保留状态。transaction/COPY/exclusive 逃生门要等独占句柄语义闭环后再开放。
- 三系统只保留一种链接配置：`KU_PG_LIB` 必须指向绝对、专用的小目录。构建过程不执行 `PATH` 中的 `pg_config`，不扫描系统安装目录，也不回退到编译器的 `-lpq`/`LIB` 搜索路径；未设置、空值、相对路径、不可读目录、扫描超限或不匹配的库都会直接失败。Windows 目录放匹配工具链的 `libpqdll.lib`、`libpq.lib` 或 `libpq.dll.a`；Ku 会有界解析 import library 并要求其目标是 `libpq.dll`。Linux/macOS 放匹配目标的 shared libpq，并分别读取 `DT_SONAME` / `LC_ID_DYLIB`。Ku 不选择 `libpq.a`，也会按 archive magic 拒绝伪装成 `.so`/`.dylib` 的 archive；链接只读取从已打开句柄复制出的私有副本，最终 PE/ELF/Mach-O 产物必须包含与本次选择完全一致的动态 loader identity。`KU_PG_LIB` 仍是可信构建输入；产物不会内嵌 libpq，部署机必须提供 loader 可见的匹配 runtime 及传递依赖。

### Redis(std.redis,自实现 RESP-over-socket,零外部依赖)

```ku
import redis from "std.redis"
fn main(): null! {
    client = redis.client({
        host: "127.0.0.1",
        port: 6379,
        username: "default",
        password: "password",
        max_connections: 8,
        max_waiters: 64,
        connect_timeout_ms: 5000,
        acquire_timeout_ms: 5000,
        command_timeout_ms: 5000
    })?
    client.ping()?
    client.set("key", "value")?
    println(client.get("key")?)
    client.del("key")?
    client.close()
    return ok(null)
}
```

- 直接在平台 socket 上实现 RESP2（Windows Winsock，Linux/macOS POSIX socket/poll/pthread），不依赖 hiredis。client 内部维护有界、懒创建连接池；构造时预连并验证 AUTH，配置中的认证信息会应用到每条新连接。
- `max_connections` 为 1～256，`max_waiters` 为 0～4096；三个毫秒 timeout 均为 1～300000。每条命令的同一总预算覆盖借连接、懒建、AUTH、发送、分段读取和 UTF-8 校验，并受 HTTP handler deadline 上限约束。
- `get` 只有严格语义：普通 bulk（包括零长度）返回 `Ok(str)`，`$-1` 返回 `redis/key_not_found`；不再提供 nil→空串或 `get_required` 的第二套写法。不要组合 `EXISTS + GET` 判断缺键，该组合存在 TOCTOU。
- 严格校验 CRLF、规范整数和长度；host/username/password 各最多 64 KiB。建连阶段的超时/transport 分别是 `redis/connect_timeout` / `redis/connect_error`，借用阶段是 `redis/acquire_timeout` / `redis/pool_busy`；只有命令发送/读取阶段的 I/O 超时仍是 `redis/timeout`，EOF/reset 等命令错误仍为 `redis/redis_error`。坏帧或已开始 I/O 后的超时会 poison 并淘汰该连接；等待池超时不会伤害其他正在工作的槽位。密码内部副本在销毁前清零；AUTH 明确拒绝固定映射为 `redis/auth_failed`，AUTH transport/timeout 归入建连阶段，任意服务端错误文本都不直接进入诊断。
- native owned `bytes` 与 plain `std.net` 基础已经存在，但 Redis 仍使用已验证的私有 RESP transport，尚未迁移到公共 bytes/net 路径。Redis 当前只承诺合法 UTF-8 文本；也尚未支持 RESP array/RESP3、TLS、cluster/sentinel 或通用 command API。

### MySQL(std.mysql,绑定 libmysqlclient)

- 唯一入口是 `mysql.client(config)!`。必填字段为 `host/user/password/database`，各字符串最多 64 KiB；`port` 默认 3306，连接/等待者/timeout 的字段名与 PG 相同。提供 `client.query(sql,[str])!`、`client.execute(sql,[str])!`、结果 receiver 读取和 `client.close()`。
- 所有 SQL（包括无参数 SQL）都经过 `MYSQL_STMT` prepare/bind/execute；不再调用 `mysql_real_escape_string` 拼接 SQL。输入参数目前只支持 `str`，尚不支持 SQL NULL、整数等 typed bind。
- 查询结果在归还连接前复制到 Ku owned、有上限的表；NULL 与 detached result 的越界/复制 OOM 保留精确错误。SQL 已进入 `mysql_stmt_execute` 后的 deadline/连接失败返回 `mysql/execution_unknown`；服务端确认成功但结果无法交付时返回 `mysql/execution_completed_without_result`。这两个错误都禁止自动重试。`execute` 只接受无结果列语句并返回 affected rows。
- pool 上限、等待者上限、懒建失败回滚和非阻塞延迟销毁与另外两个 client 同一语义；懒建阶段按先耗尽的预算区分 `mysql/acquire_timeout` 与 `mysql/connect_timeout`。libmysqlclient 的 prepare/execute/fetch 是同步 FFI：连接建立时把配置的 query timeout 设置为 read/write socket timeout，并在各阶段前后检查 monotonic absolute deadline；它不是硬截止，不能中断 C 库内部重试或同步 DNS。Oracle MySQL 文档明确说明 read 最多形成 3 倍、write 最多形成 2 倍 option 的有效等待；超时返回后驱动淘汰连接且不重放 SQL。数据库侧 timeout 仍是必需配置。[timeout 说明](https://dev.mysql.com/doc/c-api/8.4/en/mysql-options.html)
- 明确的 transaction/session-control 首语句在访问连接前返回 `mysql/session_state_unsupported`；执行后若 server status 显示事务未结束或 autocommit 已关闭，会丢弃 payload、返回同一错误并淘汰。普通完成路径中，statement 的 `free_result/close` 返回值都参与复用判定；完整读完且清理成功后再调用 `mysql_reset_connection()` 清除事务、临时表、锁和 session 变量，并重新设为 `utf8mb4`。任一步失败都淘汰单槽。每次 reset 会增加一次协议往返，但它不能撤销已经发生的数据库或外部副作用。[MySQL 官方说明](https://dev.mysql.com/doc/c-api/8.4/en/mysql-reset-connection.html)列出了 reset 清理的 session 状态。
- 自动 reconnect 和 `LOCAL INFILE` 显式关闭。MySQL 8 与 MariaDB 的 boolean bind ABI 使用条件类型适配；一次性 library init 前核对 header family/ABI major 与 `mysql_get_client_version/info`，错配返回 `mysql/client_abi_mismatch`，不进入 library init、连接或 statement API。每个 Ku main/HTTP worker 保持 thread context 到退出，密码副本销毁前清零。Unix host build 要求 `KU_MYSQL_LIB` 指向绝对、专用的 shared client 目录，`KU_MYSQL_INCLUDE` 指向对应 header；Windows 还可发现常见完整安装。编译器只链接句柄固定的私有副本，最终依赖必须与本次选择的 MySQL 或 MariaDB family 一致；不允许静态或跨 family 回退。产物不内嵌 runtime，Windows 部署通常要把同一安装根的 `lib` 和 `bin` 都放入 `PATH`；显式 non-host target 仍提前拒绝自动链接。
- 当前没有 Redis TLS，也没有可跨 Oracle MySQL/MariaDB 强制证书和主机名验证的统一配置；在该能力闭环前，Redis/MySQL 只应直连 loopback/受控私网，公网链路必须使用已验证的 TLS tunnel/proxy。不能依赖客户端库可能降级的隐式 TLS 默认值。
- PG/Redis/MySQL 的行、单元和字节限制都是单次结果上限，不是进程总内存硬上限。detached result 可以长期存活，并发查询还会叠加库内部缓冲；面向不可信查询或服务端时仍需进程级内存/并发限制。
- `sync_error` 当前覆盖可返回 Result 的 client 初始化和等待失败。锁损坏、unlock/signal/destroy 失败属于无法安全恢复的内部不变量，底层 helper 仍会终止进程；因此不能宣称所有同步原语失败都已可 catch。
- 旧 MySQL 8.0.12 的 escape-string 实库结果只证明旧实现，不能作为新 `MYSQL_STMT` client 已验收。新的 fake ABI 专项已通过，真实 MySQL/MariaDB 仍必须重新执行。

## native 标准库补齐

- **`str()`**:整数、布尔、字符串、null 转字符串,逐字对齐解释器(如 `str(-5)` → `"-5"`、`str(true)` → `"true"`)。
- **字符串方法(7/10)**:`len`(Unicode 码点计数)、`chars`(按 Unicode 标量拆分为 owned `[str]`)、`contains`、`starts_with`、`ends_with`、`replace`、`slice`(char 索引、越界返回 Result 错误)。`trim`/`lower`/`upper` 因需 Unicode 大小写/空白表,native 暂以明确错误提示,不静默偏离解释器。
- **struct 复杂字段**:支持 `[int]`/`[str]` 等基本数组字段、`[Person]` 结构体数组字段、`[[int]]` 嵌套数组字段,以及 `enum` 字段(统一拓扑发射解决 struct↔enum 布局依赖)。深拷贝/释放自动递归。
- **模板字符串**:`` `Hello {name}, age {n}` `` 在 native 下正确插值(解糖为 `str()` 拼接),此前只有解释器支持。
- **字符串字面量修复**:含非 ASCII / 非打印字符(NBSP、组合符、零宽字符等)的字面量此前在 native 下被错误转义,现已修正,`len`/`contains` 等结果与解释器一致。

## 稳定与安全

- **所有权 checker**:路径级部分 move 分析(`name = user.name` 后 `user.name` 不可用而 `user.age` 仍可用),控制流合并 initialized/moved/maybeMoved,索引位置要求显式 `.clone()`,闭包捕获值不可移出。checker 作为所有权第一道防线,backend 只执行已验证合法的 move。
- **本轮 native 回归修复**:有副作用的后续参数不再改变已求值的 Copy / 函数值参数；字符串二元左操作数、标准库方法接收者和 `array.map` 输入保留调用前快照。不同词法作用域的同名局部变量使用独立 IR 绑定；返回捕获 cell 中的 Copy 值先取值再释放 cell。新增解释器/native 差分、错误路径和分配计数回归；这些测试不等于全部 Owned 比较语义或生产峰值内存已验证。
- **内存/资源泄漏修复(经 CRT + ASan + 多智能体对抗式审计)**:
  - 修复循环内 `catch (e)` 错误绑定未释放旧值导致的累积泄漏。
  - 修复 receiver 调用中的 `?` 解包在循环内覆盖临时量前未释放旧值导致的泄漏（例如对查询结果继续调用读取方法）——服务器热路径的关键修复。
  - 修复 `array.push` owned 字面量元素未被释放的泄漏。
  - **std.pg** 统一 client 已有 fake 资源计数与 Windows loopback PostgreSQL 新 API 证据；**std.redis** bounded client 已有 fake RESP、并发 close/waiter 和错误恢复证据；**std.mysql** 已用原子计数覆盖 connection/statement/thread/library 全部归零，并注入 `free_result`、statement close、reset 和分配失败。Redis/MySQL 新 client 的真实服务与 Linux/macOS 仍列为未完成，旧驱动结果不替代新路径验收。
  - 上述泄漏是对抗式审计发现的真实缺陷,已修复并回归;但「安全」是持续过程,不代表已穷尽所有问题。

## 第三方 Package / Registry v1

- `ku package pack [path]` 生成确定性、allowlist-only 的 `.tar.zst` 源码包并做解包 round-trip 自验。
- `ku package publish [path]` 从 `KU_REGISTRY_TOKEN` 读取凭据，经 HTTPS PUT 发布；成功后重新验签 index。
- `ku package yank [path]` 使用同一 token 单向撤回当前 manifest 的 name/version；签名 index 省略该版本，但 artifact 与已有 exact lock 保持可用，不提供 delete/unyank。
- `ku package resolve [path] [--locked|--offline]` 与 `check/run/build` 共用传递依赖解析器。
- `ku.mod` 用 `registry.url` 和 `registry.public_key = "ed25519-..."` 显式固定第三方 registry；`dep.name` 保持唯一依赖语法，`@name/path` 保持唯一导入语法。
- signed index 覆盖版本、artifact URL、SHA-256 和传递 `dep.*`；resolver 有包数、求解步数、并行数和字节数上限。
- cache 命中同时校验 artifact、archive tree 和解包 tree；相同 cache key 的并发下载由有界 owner-token 租约合并。
- v1 不执行安装脚本/第三方 DLL；自动 signed-roots、在线吊销和透明 key rotation 明确留给 v2，不冒充已完成。

## 0.0.x 当前边界

- 数据库驱动目前为 native-only(`ku build --native`),解释器 `ku run` 暂不支持连库。
- 0.0.x 不承诺源码或 ABI 向后兼容；本轮统一数据库入口和 native ABI 变化都要求重新检查并构建，不保留旧写法。
- 数据库结果值目前统一为文本 `str`；类型化列、SQL NULL/typed input、transaction/exclusive、强制验证 TLS 留待后续阶段。
