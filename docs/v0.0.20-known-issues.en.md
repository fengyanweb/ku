# Ku 0.0.20: platform requirements and known limitations

- Native C, interpreter and other output paths have different coverage. Follow each feature's documentation and actual compilation result. Database clients require native output and their client libraries.
- Native C currently rejects `http.json(http.status.created, value)`. Use the equivalent integer status `201`, or the interpreter/default Runner. This limitation is reproducible in both 0.0.19 and 0.0.20.
- Linux `ku supervise` memory isolation requires writable delegated cgroup v2, the memory controller and appropriate permissions. Without these conditions, that mode cannot provide its OS-enforced limit.
- Windows uses Job Objects to limit controlled workers' committed memory; this is not RSS. macOS does not natively support this isolation mode.
- A worker OS limit covers third-party allocations inside that process. The coordinator has no equivalent OS hard limit and per-Task heap use is not precisely measured. Task/HTTP allocation ledgers are not an absolute whole-system memory cap.
- Historical workloads have shown long-tail latency and HTTP timeouts. Not all causes are confirmed and the original formal long-duration acceptance has not passed. This release does not claim those issues fully fixed or long-term stability established.
- Database cancellation/deadline observation and sending retain a timing boundary; operations near it may reach the database. Worker termination or disconnection does not prove rollback. Report uncertain outcomes honestly; business SQL is never automatically retried.
- Complete general network scheduling, full M:N, the full database platform matrix and some performance targets remain unfinished. Individual functional passes and historical local results do not establish completion everywhere.

Keep CLI, SDK, compiler and target libraries from matching builds. Source development is pinned to Rust 1.99.1; historical bundles retain the compiler identity recorded in their own metadata.
